# 0009. The transaction audit trail is a plain append-only table, written atomically with the transition it records

## Status

Accepted

## Context

Milestone 6A gave `Transaction` a deterministic state machine but no
history: reading a transaction only ever shows its *current* state, never
how it got there. M6B's job is to make that history durable and queryable
— "explain any transition after the fact" — without turning the codebase
into something it explicitly isn't (`CLAUDE.md`: "no microservices unless
a concrete future requirement justifies the split"; the M6B brief itself
rules out event buses, Kafka, CQRS, and event sourcing).

Three things had to be decided:

1. **What shape is an audit record, and who writes it?** The obvious wrong
   answer is scattering `logger.info("transaction transitioned...")` calls
   across routers — that's application logging, not a queryable domain
   record, and the M6B brief rules it out explicitly. The other wrong
   answer is a general-purpose event bus — massive overkill for "one row
   per transition, in the same database the transition itself lives in."
2. **How does a transition and its audit event stay consistent?** If
   `Transaction.state` is updated in one write and the audit row in
   another, a crash (or partial failure) between them leaves either an
   undocumented state change or a phantom "this happened" record for
   something that didn't.
3. **How is "who did this" represented, given the codebase has no
   authentication system and the M6B brief explicitly forbids inventing
   one?**

## Decision

**`AuditEvent` is a plain table, `transaction_audit_events`, with a
`BigInteger` `sequence` column generated by the database itself
(`GENERATED BY DEFAULT AS IDENTITY`)** rather than an application-computed
counter or reliance on `created_at`/UUID ordering. A UUID primary key has
no order of its own (`uuid4` is random), and two events for the same
transaction can in principle share a microsecond-resolution timestamp;
`sequence` is the one column `GET /api/transactions/{id}/audit-events`
sorts by, and it's correct under concurrent writers because the database —
not application code — assigns it.

**Exactly one place writes `AuditEvent` rows:
`app.commerce.transaction.service`.** `create_transaction` and
`transition_transaction` each add one `AuditEvent` to the session as part
of the same call that mutates (or creates) the `Transaction` row, and nowhere
else in the codebase does. No router writes an audit row directly, no other
service does either — routers stay as thin as every other router in this
codebase, and "was this recorded" always has one, unambiguous answer.

**The `Transaction` mutation and its `AuditEvent` are flushed together in
one `db.flush()` call, then committed together by the router's one
`db.commit()`.** This is the entire atomicity mechanism — no distributed
transaction, no two-phase commit, no outbox/relay pattern. It works because
both writes already share one SQLAlchemy `Session`/one Postgres transaction,
the same way `payment.service.confirm_payment` already updates `Payment`
and `Checkout` together in a single flush. Concretely:

- A transition that a guard rejects (an edge not in the FSM table, or one
  whose live domain check fails) raises *before* either write happens —
  no `Transaction` mutation, no `AuditEvent`, nothing pending in the
  session at all. This is why a rejected transition can never leave a
  misleading "success" audit row: the code path that would create one is
  never reached.
- A flush-time failure (e.g., a constraint violation) aborts the
  surrounding database transaction, so neither write lands — there is no
  window where the state changed but the audit event didn't, or vice
  versa.

**Append-only is enforced by omission, not a database trigger or an ORM
hook.** `app.commerce.transaction.repository` exposes `create_audit_event`
and `list_audit_events_for_transaction` and nothing else — no
`update_audit_event`, no `delete_audit_event`. This is the same pattern
`app.commerce.policy.repository` already uses for `PolicyDecision`
("immutable once created... rather than ever overwriting it") and
`Payment`/`MerchantPolicy`'s own "single mutable row" pattern before it —
this codebase already trusts "the function to do it doesn't exist" as
sufficient, rather than adding a database-level trigger for something no
code path attempts. `AuditEvent` rows are never deleted for the same
reason `Payment`/`PolicyDecision` rows never are: nothing in this
milestone (or any prior one) deletes those either.

**`actor_type` is a two-value closed set (`system`, `agent`), not an
identity system.** A caller states which one applies (`AuditActorType` in
the request schema); nothing authenticates that claim, because nothing in
this codebase authenticates *any* claim yet — the trust boundary here
matches every other endpoint's. Today, every transition is actually driven
through `app.commerce.transaction.router` (no `Tool` in `app.agents`
reaches it — see
`tests/agents/test_architecture.py::test_no_transaction_tool_is_declared`),
so `actor_type` is `system` unless a caller explicitly declares `agent`;
the field exists so that distinction is representable the moment it
becomes meaningful, without a schema migration.

**`AuditEvent.event_metadata` (JSONB) holds only small, transition-specific
facts not already on the `Transaction` row** — a policy decision id, a
payment id, a failure code, a checkout's expiry timestamp — populated by
each guard returning an optional `"metadata"` key alongside its column
updates. It never holds a copy of the checkout, payment, or catalog record
those facts point to; anyone needing more can already join through
`transaction_id`/the ids stored in the metadata to the tables that own that
data, the same "reference, don't duplicate" discipline
`docs/decisions/0008-transaction-state-machine-validated-by-domain-state.md`
already established for `Transaction` itself.

**The audit `reason` prefers a domain-derived explanation over a caller's
own claim, wherever a guard produced one.** A policy denial's `reason`
comes from the real `PolicyDecision.reason`, a payment failure's from the
real `Payment.failure_code` — not from whatever string a caller (including,
eventually, an AI buyer) might supply. A caller-supplied `reason` is used
only for edges with no domain fact to derive one from (e.g. an explicit
cancellation) — see `transition_transaction`'s `audit_reason` resolution.

**Transaction creation is itself recorded as an audit event**
(`from_state=None`), not left as an implicit, unaudited starting point.
Without this, the audit trail would have a gap at exactly the moment a
transaction came into existence.

## Consequences

- The audit trail can only ever describe transitions made through
  `app.commerce.transaction.service` — it has no visibility into (and does
  not attempt to reconstruct) checkout/policy/payment history from before
  M6A, or events in domains that don't route through `Transaction` at all.
- Because `sequence` is a database-generated identity column, retrieval
  ordering is exact and gap-tolerant (a rolled-back insert can consume a
  sequence value without leaving a visible row) — this is expected and
  does not indicate a missing event.
- "Append-only" is a codebase-level guarantee (no code path updates or
  deletes a row), not a database-level one (a direct `UPDATE`/`DELETE`
  against `transaction_audit_events` is not physically prevented). This
  mirrors every other "immutable" record already in this codebase
  (`PolicyDecision`, `Payment`'s row-per-checkout history) and was judged
  sufficient for the same reason: a trigger or revoked grant would be
  meaningful additional infrastructure for a guarantee this milestone
  doesn't need stronger than "no code writes it."
- Per-transition audit metadata is intentionally sparse. A future milestone
  wanting a full reconciliation/compliance export of every fact behind a
  decision would need to join back to the referenced checkout/policy/
  payment rows by id — this was a deliberate trade against duplicating
  those records into every audit row.
